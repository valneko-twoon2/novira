# Multilingual support (`frontend/src/i18n/`)

Follow this when adding, changing or removing screen text, and when adding areas or languages. For the procedure (how to use `i18n-add.mjs`, how to add and remove areas and languages), see the `/i18n` skill. The current languages are defined by the folder names under `frontend/src/i18n/locales/` (ja, en, zh-CN, zh-TW, ko, ru, es, pt-BR, fr, de).

## 1. What to follow

- **Never hard-code text.** Do not write user-read text in ts/tsx: displayed text, `aria-label`, `placeholder`, `title`, notifications, error displays. Use `t('<key>', { name: value })`; for sentences whose form changes with a count, use `tCount('<key>', count)` (the keys are `<key>.one` and `<key>.other`).
- **ja and en are always complete; the other languages follow later.** When adding text, add the key to ja and en in the same change (never one of the two, never empty). The other eight languages (zh-CN, zh-TW, ko, ru, es, pt-BR, fr, de) may lack it: `t()` shows the English text until a translation is added. Do not write the eight by hand for each change; they are filled in one batch (`node frontend/scripts/i18n-todo.mjs` lists what is missing, `i18n-add.mjs --fill` adds the translations; see the `/i18n` skill). Translate them when a piece of work ends, before a release, or when the user asks.
- **When you change what ja and en show, never leave an old text in another language.** The same goes for rewording and changing a placeholder. `i18n-add.mjs --replace` removes the other languages' old text for a key it is not given new text for (it falls back to English), so use it instead of editing the files. Removing a key removes it from every language. Only when you intentionally fix a single language (for example a typo), commit with `NOVIRA_I18N_SINGLE_LOCALE=1` and write the reason in the report.
- **Catalogs**: `locales/<language>/<area>.json` (flat JSON, split by area). `ja` is the source of truth; en has exactly the same keys as ja, and every other language has only keys that ja has (and the same placeholders). Create a new area's file for every language and register it for ja and en in `src/i18n/catalog.ts`. ja and en are built into the app; every other language is a chunk loaded when it is chosen (`src/i18n/bundles/<language>.ts` takes the area files of its folder), and `setLocale` switches once it has loaded, so `t()` stays synchronous. Tests that check every language at once read `src/i18n/catalogs.testkit.ts`, or call `loadLocales()` first.
- **Keys**: `<area>.<content>`, lowercase, dot-separated. Variable parts are `{name}` (the same name in every language; literal braces are `{{` `}}`). Do not build a sentence by concatenating fragments.
- Do not evaluate `t()` at module load time (use a getter or a function).
- **Do not translate**: engine names such as models, LoRAs and schedulers, enum values, `data-testid`, shortcut chords. **Out of scope**: `src/backend/mock/` and tests.
- Keep terminology consistent within each language. Use the same word for the same concept (board, gallery, queue, and so on), and look for the existing translation first. **The terminology list is `src/i18n/glossary.json`**: per concept the canonical ja and en word and the variants that must not be used (for example ja `導入` / `入れる` for installing, which is `インストール`; "pack" for an extension; British spellings; `HuggingFace`). Read it before you write text. Engine concepts use ComfyUI's own word. `docs/glossary.md` says what the words mean and does not repeat the list.
- **Adding a term**: when you settle a word, add an entry to `terms`: `concept`, `ja`, `en`, `why`, and `avoid` (regexes per language, `*` for names spelt the same in every language). Write the regex so that the meanings the word may keep stay allowed (lookarounds: `入れる` stays for typing and for the queue); `keys` limits a rule to catalog keys (for example `\.status\.`), and `except` lists single keys with a reason. No blanket exceptions: fix the text instead. Run `node frontend/scripts/check-glossary.mjs` (ja and en); `NOVIRA_GLOSSARY_LOCALES=all` (or `ko,de`) checks the other languages when they are asked for.
- **Check whether the manual uses the text.** The manual pulls screen text with `{{ui:<key>}}`, so removing a key, renaming it or adding a placeholder breaks the build and tests. Fix the chapters that use it ([manual.md](manual.md)).
- **When adding or removing a language, align every area of the app, the language list, the settings screen, the E2E tests and `docs/manual/<language>/` in the same commit.** Do not leave a partial language.

## 2. Machine checks

| Check | What it stops |
|---|---|
| `tests/i18n.test.ts` | A key ja has and en lacks, a key in another language that ja does not have, different area files or placeholders across languages; hard-coded Japanese in ts/tsx |
| `tests/i18n-glossary.test.ts`, `scripts/check-glossary.mjs --staged` (pre-commit, when a ja/en catalog, a ja/en chapter or the list is staged) | A word `src/i18n/glossary.json` says to avoid, in the ja and en catalogs and manual (other languages with `NOVIRA_GLOSSARY_LOCALES`); a term without a canonical word or reason, a bad regex, an exception for a key that does not exist |
| `e2e/layout.spec.ts` (text fit, `e2e/textFit.ts`; `node tools/layout-scan.mjs`) | In ja and en (`--locales all` for every language), text clipped by its frame, overflowing a button, or a short name wrapping midway, also in tooltips and menus. When you add a screen, add it to the spec's list too |
| `scripts/check-i18n-sync.mjs` (pre-commit) | A commit that changes ja or en without the other, or leaves another language a text for a message that ja or en changed |
| `scripts/check-manual-sync.mjs` (pre-commit) | A manual chapter changed in ja or en without the other, or in neither translated nor listed as pending for another language |
| `tsc` | A nonexistent key (the `t()` keys are typed from ja), a missing entry in `Record<Locale, …>` |
| `tests/manual.test.ts` | A manual `{{ui:…}}` key that does not exist, an app language with no manual folder |

## 3. Reporting

When you add or change text, areas or languages, write what ja and en received, how many messages the other languages still lack (`i18n-todo.mjs`) or whether you filled them, and whether you updated the manual chapters (and the reason if not).
