# Verifying changes

How to check a change, from the cheapest check to the real app. Run the cheapest check that can catch the failure you are worried about, and say in the report which levels were run and which were not.

## Levels

| Level | What it catches | How |
|---|---|---|
| 1. Static and unit | Types, lint rules, line ends, message catalogs, pure logic, Rust library behaviour, the wire contract, the ComfyUI prompts we build, and that a real ComfyUI accepts them (node names, inputs, links, choices, limits; `comfy::node_defs_check`) | `npm run typecheck`, `npm run lint`, `npx vitest run <path>` in `frontend/`; `cargo fmt --all`, `cargo test -p novira-core --lib`, `--test <name>`, `cargo test -p novira` (IPC command list and capabilities) in the repository root; all of it at once: `npm run check` (frontend) or `scripts\check.bat` (both) |
| 2. Mock in a browser | Layout, screen flow, anything that does not need ComfyUI | `npm run e2e` (Playwright user flows and screenshot comparison; it starts its own dev server on port 5180, or `E2E_PORT` when several checkouts run at once); for a quick look, `npm run dev` then `node scripts/shot.mjs --url <URL> --out <png> [--click <selector> ...]` ; `node tools/layout-scan.mjs` (repository root) scans every screen for layout faults and text that does not fit |
| 3. Real engine, no window | The queue worker, the graphs on the real ComfyUI, model files and where they must live, the GPU: what a job does from the queue to the file | `models_live` (below); the agent runs it |
| 4. Real app, isolated | The window itself: IPC commands, the WebView (image and video display, CSP), start-up, the screens' own requests | the recipe below; **the user's check by default**. Anything a browser can check runs in Playwright's Chromium on `novira-server` instead (`tools/server-run.mjs`, `models-sweep.mjs --via server`): the window is only for what needs it. The agent runs it for a change to the IPC layer, the shell (`src-tauri`), the WebView set-up or start-up, and as the model sweep (below) for a model change |

The mock backend answers instantly and never fails the way ComfyUI does, so a feature that touches the engine, the queue worker, model files or packs is not verified until level 3 has run (or the report says it was not). Level 3 finds what the mock and the fake ComfyUI cannot (a checkpoint saved in a folder ComfyUI does not read, a dry run that built a picture job without a picture); it does not see the screens, so a change to what the screens send or show is still looked at in level 2, and the whole path in the window is level 4.

## Documentation-only changes

A change that touches only `AGENTS.md`, `README.md`, `docs/`, `.claude/rules/` or `.claude/skills/` skips the tests and lint; say "documentation only, skipped" in the report. Exceptions: `docs/manual/` runs `tests/manual.test.ts`, and the map and design pages run `tools/docs-check.mjs`. `npm run check:eol` always runs.

## Kinds of tests

| Kind | Where | Run | Update on purpose |
|---|---|---|---|
| Unit and component | beside the code (`*.test.ts[x]`, `#[cfg(test)] mod tests`) | `npx vitest run <path>`, `cargo test -p novira-core --lib` | — |
| Property and fuzz-style | `backend/crates/novira-core/tests/prop_*.rs` (proptest, fixed seed, in process; the only HTTP is the loopback fake site) | `cargo test -p novira-core --test prop_paths` (`prop_graph`, `prop_parsers`, `prop_roundtrip`, `prop_loopback`); `PROPTEST_CASES=<n>`, `PROPTEST_SEED=<n>` | a failing input is pinned as an ordinary test, never as an ignored one |
| Mutation fuzzing | `backend/crates/novira-core/tests/fuzz_inputs.rs`: valid pictures (PNG, JPEG, WebP, GIF, BMP, with text and XMP), signed content credentials, model headers and a backup zip, each damaged one to four times (bit flips, cuts, inserts, copied ranges, edge-value length fields, splices) and read again: no panic, no reader slower than 10 s, a backup refused or unpacked only into the staging folder. Stable Rust, a small seeded generator, no fuzzing engine | in `cargo test -p novira-core` (200 cases per reader); a longer search with `NOVIRA_FUZZ_ITERATIONS=20000 NOVIRA_FUZZ_SEED=<n>` | an input that panics is saved to `novira-data/work/fuzz/` and pinned as an ordinary test next to the reader |
| Property and fuzz-style (frontend) | beside the code (`*.property.test.ts[x]`, fast-check; setup in `frontend/src/propertyTest.testkit.ts`; in process only, `fetch` stubbed to throw, fixed seed) | `npx vitest run <file>.property.test.ts`; `NOVIRA_PBT_RUNS=<n>`, `NOVIRA_PBT_SEED=<n>` | a failing input is fixed in the app, or kept as an `it.fails` test with a `known bug:` comment until it is |
| Service integration | `backend/crates/novira-core/tests/backend_service/` (fake engine), `comfy_fake_server/` (fake ComfyUI) | `cargo test -p novira-core --test <name>` | — |
| Contract | `contract/*.json`, checked by `frontend/src/backend/contract.test.ts` (samples in `contract/samples/`), `frontend/src/backend/tauri/commands.contract.test.ts` and `backend/crates/novira-core/tests/contract/` | `npx vitest run src/backend/contract.test.ts src/backend/tauri`, `cargo test -p novira-core --test contract` | change the sample, then `CONTRACT_UPDATE=1 npx vitest run src/backend/contract.test.ts`, then the Rust check |
| ComfyUI prompt snapshots | frontend `features/*/__snapshots__/`, backend `src/comfy/__snapshots__/graph/` (`graph_snapshots.rs`, and `graph_snapshots_families.rs` for the newer model families) | `npx vitest run <file>.snapshot.test.ts`, `cargo test -p novira-core --lib comfy::graph_snapshots` | `npx vitest run -u <file>`, `UPDATE_SNAPSHOTS=1 cargo test -p novira-core --lib comfy::graph_snapshots` |
| Node definitions | `src/comfy/__snapshots__/node-defs.json`, the definitions of a real ComfyUI for the nodes the snapshots use; `comfy::node_defs_check` tests every backend snapshot prompt against them | `cargo test -p novira-core --lib comfy::node_defs_check` | start a ComfyUI (`--cpu` is enough), `node tools/comfy-node-defs.mjs http://127.0.0.1:<port>`, read the diff. Do this when a graph gains a node, and to follow a newer ComfyUI |
| Old data folders | `backend/crates/novira-core/tests/fixtures/data-<version>/`, each written by that release's own code; `tests/backend_service/old_data.rs` opens a copy in another folder and checks every board, picture, file, setting, workflow, comic and job is there and a new job still runs | `cargo test -p novira-core --test backend_service old_data` | never rewritten. At a release, on its commit: `cargo run -p novira-core --example make_old_data_fixture`, copy `novira-data/work/fixture-out/` without `extra_model_paths.yaml` to `data-<version>/`, add one test line |
| Mock against the backend (differential) | `frontend/difftest/*.difftest.ts`: the same calls (boards, workflows, comics, canvas, screen state, uploads and gallery edits) to `MockBackend` and to the real backend through `novira-server` on an empty data folder with no engine; made-up ids, times and picture addresses are numbered before comparing, a refusal is compared as a refusal | `node tools/diff-backends.mjs` (`--build` rebuilds the server) | a difference is fixed in the mock, or the case leaves that part out with the reason |
| End-to-end | `frontend/e2e/*.spec.ts`; the phone layout (`phone*.spec.ts`) in Chromium (`phone`) and in WebKit as an iPhone (`webkit`; Playwright's WebKit, not iOS Safari) | `npm run e2e` (or `npx playwright test --project=chromium` for the flows only) | — |
| Visual regression | `frontend/e2e/visual.spec.ts`, baselines in `e2e/__screenshots__/` (one set per platform: `-win32` from Windows, `-linux` from the cloud container; a change to a screen updates the set of the machine it ran on, so the other set is refreshed the next time it runs there) | `npm run e2e:visual` | `npm run e2e:visual -- --update-snapshots` (the pre-commit hook runs this check when a staged file can change a screen and refuses the commit until the baselines are updated; look at the new images first) |
| Layout scan and text fit | `frontend/e2e/layout.spec.ts` (the `layout` project), measured by `e2e/layoutScan.ts` and `e2e/textFit.ts`, judged by `e2e/layoutRules.ts` (unit tests `tests/layout-rules.test.ts`) | `node tools/layout-scan.mjs` from the repository root (ja and en, dark and light, about two minutes with 6 workers; `--locales all` for every language, only when asked) | — (no baselines: a fault is fixed, or the place is marked as designed) |

The layout scan opens every main screen, the side bar, the media screens and the dialogs that are cheap to open (settings panes, hotkeys, about and licenses, the gallery's settings, picture menu and the dialogs its items open, the viewer, the node picker, the model view and import, the browse detail, the extension detail and versions, the assistant and its popovers, the dynamic prompts and pose presets), with the folded sections opened, and reports four kinds of fault from the real layout: `overflow` / `offscreen` (a control sticks out of the box that holds it, or out of the window; a row that scrolls sideways on purpose is fine), `clipped` (text cut off by a box that hides overflow), `truncated` (text shortened to "…" by an ellipsis or a line clamp), `touching` / `overlap` (two visible controls or rounded cards of one surface less than 1px apart, or overlapping; a joined group whose facing corners are square is fine). A place designed to shorten text carries `data-truncate-ok`, boxes joined on purpose `data-touch-ok`, and decoration the scan must skip `data-layout-ignore`; each one needs a reason in a comment. The same pass checks the text fit (`e2e/textFit.ts`: a label cut off, sticking out of its button or broken in two, a tooltip, menu or dialog out of the window), on the main screens also every tooltip (shown by focusing its trigger, all in one call in the page) and every menu, popover and picker they open (those of the side bar, the gallery panel and the Invoke bar only on the Generate tab, and an opener repeated down a list, such as the menu of every model row, once). Each surface is opened once per language in the dark theme; after each step the theme is switched in place to light and the layout measured again, since the themes differ only in colours and only the rules about drawn boxes depend on them. `LAYOUT_SHOTS=<folder under novira-data/work/>` also saves a screenshot of every scanned step, to look at by eye. A pass is recorded in `novira-data/work/layout-scan/passes.json` with a hash of the layout source (css, `src/ui/`, `src/app/`, feature tsx, the scan itself); the pre-commit hook refuses a commit that changes layout source unless a recorded pass in ja and en has the hash of exactly what is staged (`node tools/layout-scan.mjs --check` tells whether the working tree has one). The scan opens a minified build in the harness mode (`HARNESS_MODE` in `tools/harness-paths.mjs`, also used by the verification app and the browser server: what only the app's `production` build leaves out, such as the media tabs hidden for now, stays in; `frontend/scripts/e2e-server.mjs`, kept in `novira-data/work/e2e-build/` and rebuilt only when its sources change; the dev server compiles every module of every page on demand), and holds the e2e lock (`tools/e2e-lock.mjs`, a directory in `novira-data/work/` like the GPU lock, taken over when its process is gone) so a second heavy run waits; any other Playwright run can take it with `node tools/e2e-lock.mjs -- <command>`. It uses half the processors as workers, never more than 6 (`--workers <n>` is capped too; `frontend/playwright.config.ts` has the same cap): more left the user's PC too slow to work on, and on 16 processors 12 workers were no faster and 16 made cases time out. Limits: only the surfaces in the spec, at 1600x900; other languages only with `--locales all`.

Read every snapshot, fixture or baseline diff before committing it; an update is a statement that the new output is intended.

Live tests that need the network, the `claude` / `codex` CLI or a running ComfyUI are `#[ignore]`d under `backend/crates/novira-core/tests/`; run them by name with `-- --ignored` only when the change is about that integration.

## Whole-repository checks

| Command / file | Runs | Not included |
|---|---|---|
| `npm run check` (in `frontend/`) | `typecheck`, `lint`, every vitest test, `check:eol` | Playwright (`npm run e2e`): it takes minutes and needs a browser |
| `node tools/affected.mjs` (repository root; `--list`, `--e2e`, `--base <ref>`, or paths) | the checks the changed files need, by the tables of `.claude/rules/regression-tests.md`: typecheck, eslint and stylelint on the changed files, `vitest related` (every test that imports a changed file), the tests that read a changed catalog, chapter, fixture, record or map page, `cargo fmt --check`, clippy, the novira-core library tests and the integration tests that name the changed module, `-p novira` for the shell, line ends. A build setting or dependency runs that whole side | Playwright unless `--e2e` (then the specs named after the changed feature, all flows for a shared part, and the visual regression); integration tests that reach the module only through another module; live tests |
| `scripts\check.bat` (run from the repository root; `scripts\check.bat frontend` / `scripts\check.bat backend` for one side) | `npm run check`, `cargo fmt --all -- --check`, `cargo clippy -p novira-core --tests -- -D warnings`, `cargo test -p novira-core`, `cargo test -p novira`; every step runs, the exit code says whether any failed | Playwright, ignored live tests. `cargo test -p novira` builds `target\debug\novira.exe`, which Windows locks while novira is open: then it builds into `novira-data\work\check-target` (as `affected.mjs` does; `check.bat` first deletes stale output, see "Where the harness writes" below), unless `CARGO_TARGET_DIR` is set |
| `scripts\full-check.bat` (`tools/full-check.mjs`; `--no-browser`, `--list`) | `scripts\check.bat`, `cargo test -p novira-server`, `tools/diff-backends.mjs`, the Playwright projects chromium, phone, webkit and visual (under the e2e lock), the layout scan; every step runs, a report with each step's result and the end of a failed step's output goes to `novira-data/work/full-check/<time>.md` | live tests, the mutation run, the real app. Started by hand: there is no CI |
| `npm run check:eol` | `git ls-files --eol` over tracked files and untracked files that are not ignored; fails on LF or mixed line ends (binary files skipped; `eol=lf` in `.gitattributes` is honoured) | the staged blob (it reads the working tree) |

Reports in `novira-data/work/coverage/` | branch coverage of Rust. Not run by any check script. The combined (unit + E2E) figure counts lines only, and the two tools count lines a little differently, so read it as approximate |
| `scripts\mutation.bat rust` (`-- -f <file>` for one file) | whether the Rust tests catch real changes of the code: cargo-mutants mutates novira-core and reruns the tests; a surviving mutant means a test gap. | `.githooks/pre-commit` (turned on by `npm install` in `frontend/`, the `prepare` script) | refuses staged `novira-data/` (including `novira-data/work/`), `data/`, `outputs/`, `out/`, `config.json`, `.env*`; line ends of the staged files; a message changed in ja or en without the other, an out-of-date text in another language, a manual chapter not translated or listed as pending; layout source without a recorded layout-scan pass on what is staged (it checks the record, it does not run the scan) (`.githooks/pre-commit.mjs`, `check-i18n-sync.mjs`, `check-manual-sync.mjs`) | anything slow; it is skipped by `--no-verify`, which agents do not use |

Rules that these checks enforce, with their limits written at the top of each file:

- Layer boundaries (`frontend/scripts/eslint-layers.mjs`, an ESLint rule): `backend/` imports none of `state/`, `ui/`, `features/`, `app/`; `i18n/` and `theme/` import none of the layers; `state/` not `ui/`, `features/`, `app/`; `ui/` not `features/`, `app/`; a feature not another feature except `features/media`. Both `@/` and relative specifiers are resolved. The imports that broke the rule when it was added are listed one by one in the same file; `frontend/tests/structure.test.ts` fails when an entry is no longer needed, so the list only shrinks.
- No catch-all folders (`utils`, `misc`, `helpers`) under `frontend/src/` (`frontend/tests/structure.test.ts`).
- No committed `.only` in vitest or Playwright sources (`frontend/scripts/eslint-test-hygiene.mjs`; aliases and computed names are not caught).
- `#[ignore]` only in `backend/**/tests/*_live.rs`, and no ComfyUI prompt snapshot file without a test case that writes it, frontend and backend (`frontend/tests/test-hygiene.test.ts`). The scan reads literal names and one-argument `snap('name')` helpers; a test that builds names at run time must check its own folder (as `comfyPrompt.snapshot.test.ts` does). `contract/` fixtures have their own orphan checks on both sides.

## Real engine, no window

`backend/crates/novira-core/tests/models_live.rs` opens the data folder with `Backend::open`, runs the worker, queues one job and reads the file back, on the real ComfyUI the data folder's `settings.json` points at (`{"comfyuiDir": ...}`, a copy, as for the real app below). No window, no second build of the app, no Playwright: a run takes under a minute once the test binary is built (measured on 2026-10-12: LTX-Video text to video 40 s, Anima 1024 px 41 s, both including the start of ComfyUI).

```text
NOVIRA_GPU_LOCK=<the lock directory> node tools/models-live.mjs <part of the model name> [--image <file>] [--out <folder>]
```

The wrapper (repository root) sets `NOVIRA_LIVE_DATA` to `novira-data/work/verify-data` (or `NOVIRA_VERIFY_DATA`), refuses a data folder that is not strictly inside `novira-data/work/` or one without a `settings.json`, adds the shared model folder to that `settings.json` (below), puts cargo on PATH, runs the GPU check below, and then runs `cargo test -p novira-core --test models_live -- --ignored --nocapture` in `backend/`; the other `NOVIRA_LIVE_*` variables pass through.

The model is found among the installed models of the data folder (the file and what it needs, the encoders and the VAE, are in its `models/`), and the family decides steps, CFG, size and frames (`preset` in the test). `NOVIRA_LIVE_IMAGE` starts an image to image or image to video job, `NOVIRA_LIVE_STEPS`, `_CFG`, `_SIZE`, `_FRAMES` change the numbers, `NOVIRA_LIVE_OUT` saves the result for a look by eye. The worker takes the GPU lock itself; check that the user is not using the GPU first. Before a script downloads into the data folder, check that its model folders are real folders: one may be a junction to the user's own `novira-data/models/...` (`Get-ChildItem <data>/models | Select Name, LinkType, Target`), and a download there lands in the user's models. A test that needs a different job (inpaint, a control layer, a Wan 2.2 pair) goes in the same file. `*_live.rs` stays `#[ignore]`, run only on purpose.

It is the same engine path as the window: what it cannot see is the part between the screen and `Backend` (the request the screen builds, IPC, the WebView). Say in the report which of the two ran.

## Real app, isolated

The debug executable embeds a built frontend: the app's own is `frontend/dist` (`build.rs` rebuilds it only when it is missing or older than the sources). The verification build embeds the harness build instead (`buildHarnessDist` in `tools/harness-paths.mjs`, in `novira-data/work/e2e-build/`), so every screen is in it and nothing of the harness lands in `frontend/dist`, which the user's next `cargo build` would embed. Use a separate Cargo target folder so a running novira (Windows locks its exe) does not block the build.

```text
node frontend/scripts/e2e-server.mjs --build-only
cd backend && CARGO_TARGET_DIR=<temp>/novira-verify NOVIRA_SKIP_FRONTEND_BUILD=1 TAURI_CONFIG='{"build":{"frontendDist":"<the e2e-build folder>"}}' cargo build -p novira
```

Start it with its own data and browser profile, and a debugging port to drive it:

| Variable | Value |
|---|---|
| `NOVIRA_DATA_DIR` | a folder strictly inside `novira-data/work/` (default `verify-data`), never `novira-data/` itself: that holds the running app's lock, queue and images |
| `WEBVIEW2_USER_DATA_FOLDER` | `novira-data/work/verify-webview` (without it WebView2 fails while the user's novira runs) |
| `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` | `--remote-debugging-port=9333` |

Drive the window with Playwright `chromium.connectOverCDP('http://127.0.0.1:9333')` (`@playwright/test` in `frontend/node_modules`). Context menu items do not forward `data-testid`; select them by role and name.

Models are kept outside the repository. Verification may use models under non-commercial licences (FLUX.1-dev, NoobAI-XL and the like).

An empty data folder makes the app download its own ComfyUI on first start. To skip that, or to keep custom node pack installs away from the user's engine, point the isolated data folder at a copy of ComfyUI: put `{"comfyuiDir": "<copy>/ComfyUI"}` in its `settings.json`. Models and pack files can be copied or downloaded into that data folder.

### Harness: run one check, then clean up

`node tools/verify-real-app.mjs <test.mjs> [--build] [--keep]`, run from the repository root, runs one test script against the isolated app and cleans up afterwards. First it checks the script with `tools/ui-refs.mjs` and stops when the script names a test id or screen-text key the screens no longer have (before minutes of build). It builds the verification exe when it is missing (`--build` rebuilds it first; the frontend in the harness mode, so every screen of the app is in it), starts it with the variables above (`NOVIRA_GPU_LOCK` is passed on when the shell sets it), waits for the debugging port, and runs the test with `node`. Afterwards, in every case, it closes the verification window (forcing it after 15 s, and only its own process tree), stops the verification ComfyUI (python processes whose command line contains `comfy-copy`), and deletes the verification exe: `debug/novira.exe` and the copies cargo keeps in `debug/deps/` (`novira.exe` or `novira-<hash>.exe`), all in the verification target folder. Test binaries such as `novira_core-<hash>.exe` are not the app and stay. `--keep` leaves the exe in place.

Before it starts or deletes anything, the harness refuses to run when the verification target folder is inside the repository, when the exe would be one of the user's own `novira.exe` files, or when the data folder or the WebView2 profile is not strictly inside `novira-data/work/` (`novira-data/` itself, `work/` itself and anything outside are refused). Environment: `NOVIRA_VERIFY_TARGET` (default `<temp>/novira-verify`), `NOVIRA_VERIFY_DATA` (default `novira-data/work/verify-data`). Because the exe is deleted, a later run builds it again first, which takes a few minutes. `--release` builds and runs the release exe instead. `--no-engine` writes into the data folder's `settings.json` a `comfyuiUrl` on a closed loopback port, takes out `comfyuiDir` and `comfyuiPython` and turns the Civitai lookup off, so the app owns no ComfyUI process and installs none (the engine shows as unreachable), and skips the GPU check; when the run ends, `settings.json` is put back as it was (or removed if the run created it), so a later run with the engine does not find the closed address. The test script gets `NOVIRA_VERIFY_APP_PID` and `NOVIRA_VERIFY_STARTED_AT` (epoch ms of the spawn).

## Model sweep

`node tools/models-sweep.mjs [--category <name>] [--model <part>] [--no-gpu] [--build] [--lookup]` runs the isolated app with the Civitai lookup off and checks every installed model: listed on the Models screen with its rail entry and base, its cover (on the card and the Generate screen's model card; the picture must load), offered by the screen that draws with it; and, with the GPU free and `NOVIRA_GPU_LOCK` set, for one model per kind and base, one job from its screen whose graph, read back from the verification ComfyUI's `/history`, loads that file, with a picture that is not blank. Each model pack (video, music, voice, inpaint, logo, turbo) is a row with the listing check only: its files in any model root against the app's pack status. Files on disk the app does not list fail too. The table, the record and the screenshots go to `novira-data/work/models-sweep/<time>/`. When to run it and what to do with a failure: `.claude/rules/models.md`. `--lookup` adds a second round with the lookup on; it sends the hash of every model file to Civitai, so it runs only when asked (also with `--model` or `--category`), and without it the cover check for the lookup-on case reads "not run (use --lookup)". The record of an off-only run still covers HEAD for the Stop hook and `tools/affected.mjs`: the gate asks for the off round and the GPU part, not for the network round. A pass is about the files of that run; the job part covers one model per kind and base, not each model.

### Through the browser server

`node tools/models-sweep.mjs --via server [...]` runs the same checks a to e without the desktop window: `tools/server-run.mjs` brings the harness build of the frontend up to date and builds what is missing (`novira-server` into `novira-data/work/server-target`, `NOVIRA_SERVER_TARGET` to move it), starts `novira-server --data <verification data> --dist <the harness build> --engine` and Playwright's own Chromium opens the printed address, with the e2e lock held; `models-sweep-app.mjs` then calls the backend by `POST /api/<command>` instead of Tauri IPC and reads ComfyUI's `/history` as before. The data folder, the shared models (`modelRoots`) and the engine copy are the same as the app run's, so the app and the server cannot run on it at once (one process per data folder), and the GPU lock comes from `NOVIRA_GPU_LOCK` (the server's worker takes it; do not hold it by hand). Checked on 2026-10-21 against the app path on a checkpoint (`waiIllustriousSDXL_v170`), a LoRA (`ryugahama_yueilxl_v1`) and a pack row (`music pack`): the same verdicts, the same graphs (only the seed differs), jobs of 11 to 18 s against 12 s in the window. What the browser path cannot check: the `novira-image://` scheme (pictures come from `/novira-image/`), WebView2's rendering and its GPU paths, the native dialogs and the commands behind them (`api::SHELL_ONLY`), and the window's own startup. Because of that a `--via server` record is marked (`via` in `sweep.json`) and does not cover HEAD for the Stop hook. A one-picture run through the page (2026-10-21, `waiIllustriousSDXL_v170`, 768x768, 12 steps): the queue item went pending, in progress (the generating strip showed 0.3 s after the click, `invocation_progress` over `/events`) and completed in 6.4 s, `image_added` followed, the gallery showed the 256 px thumbnail from `/novira-image/thumb/`; a second 50-step job cancelled from the Queue tab came back as `canceled` over the socket. The page is usable after about 20 s, the engine's start (the window's splash gate). A narrowed run (`--model`, `--category`) no longer reports the files of other models as "not listed".

## Measuring speed

`node tools/perf.mjs <backend|startup|app|all>` (repository root) measures processing, start-up and communication time the same way in every session. No part starts ComfyUI or uses the GPU, and nothing of it shows on a screen.

| Part | What it times |
|---|---|
| `backend` | `backend/crates/novira-core/examples/backend_timing.rs` in release: each step of `Backend::open` on a fresh copy of the data, and 20 samples of each command the screens call at start and often (the call, its JSON, the browser server's dispatch), with the size of the answer |
| `startup` | `tools/perf-startup.mjs`: a production build in Chromium on `novira-server` (or `--via mock`), from the request to the visible thumbnails, long tasks, and the app's own marks and call times; `--switch` adds the screen switches, `--dist a=<folder> --dist b=<folder>` interleaves two builds |
| `app` | the real desktop app in release, isolated (`verify-real-app.mjs --release --no-engine`): per run a new process and then a reload, read over CDP; the only part that times Tauri IPC. A python process under the app fails the run |

The app notes its start (`backend-ready`, `app-loaded`, `bootstrap-received`, `stores-filled`, `shell-visible`, `first-thumbnail`) and every backend call (name, start, duration; the last 500) in `frontend/src/backend/perf.ts`; the harness reads `window.__noviraPerf.snapshot()`. The size of each answer is noted only once the session storage key `novira-perf-record` is `1` and the page reloaded, since it turns each answer into JSON text.

The data is `novira-data/work/perf-data` (`--data` for another folder inside `work/`), a copy of real data whose `modelRoots` name the shared models. It is copied to `work/perf/source` with the roots written as Windows paths: a root written with forward slashes does not equal the paths the database stores, and every open then reads all model headers again (about 250 ms), which the user's app does not do. Each part runs `--runs` times (default 7) and keeps every sample.

To judge a change: `node tools/perf.mjs all --save before` on the code before it, `node tools/perf.mjs all --compare before` after it (or `node tools/perf.mjs compare before` on the latest result). A metric moved when its new median is outside the baseline's lowest to highest sample and differs by at least 10 % and 2 ms (1 for a count); a size when it differs by more than 1 %. Everything else is noise. `agent_status` is shown but never flagged: it runs the assistant CLIs, which answer in 45 or in 270 ms by their own whim. The console shows what moved and a few headline metrics; `work/perf/<name>.md` has every metric, the comparison and, for `app`, the IPC table: per command the time in the window (cold and warm) beside the backend's own time (the call plus its JSON), whose difference is what the IPC way costs. Results are `work/perf/<name>.json` and `latest.json`, baselines `work/perf/baselines/<name>.json`. Compare only timings taken on the same machine. A heavy job of the user's (a build, a generation, another agent's run) moves them: each part notes how busy the processors were before it and during it (`load` in the result, a line in the comparison, a warning above 20 % before a part), so read that line first and repeat a run that flags something while the load differs. A compare of unchanged code on 2026-10-21 flagged none of 167 metrics on a quiet machine (5 to 12 % busy before each part), and the warm `app-loaded` (+11 %, one run at twice its time) when something else ran in between. The recorder costs about 0.13 µs per call when off (Node, 200 000 calls); a start with it against one without, nine runs each, interleaved, differed inside the noise.

## Where the harness writes

One root, `novira-data/work/` of the main checkout (from a worktree too: `tools/harness-paths.mjs` takes the first entry of `git worktree list`, and the shared models are that checkout's `novira-data/models`, or, when the Settings screen moved the data folder out of the repository, the `models/` of the folder the pointer in `%LOCALAPPDATA%\novira` names, the debug build's first; a ComfyUI copy the move took along in its `work/` is used too), with these entries (all git-ignored through `novira-data/`):

| Entry | What | Deleted when unused for |
|---|---|---|
| `verify-data/` | the isolated app's data folder (`NOVIRA_VERIFY_DATA` may name another one inside `work/`), its `settings.json` lists the shared model folder | 30 days |
| `verify-webview/` | its WebView2 profile | 30 days |
| `comfy-copy/` | the copy of ComfyUI (a copy, so a pack install never touches the user's engine); python processes are recognised by this folder's name | 30 days |
| `check-target/` | the Cargo target of `check.bat` and `affected.mjs` while the user's `novira.exe` is open | 14 days |
| `server-target/`, `layout-scan/` | the Cargo target of the browser server (`tools/server-run.mjs`); the layout scan's pass record | 14 days |
| `perf-data/`, `perf-target/`, `perf/` | the data the speed measurement runs on (below), its release builds, its results and baselines | 30, 14 and 14 days |
| `coverage/`, `mutation/`, `manual/`, `models-sweep/`, `e2e-build/` | reports, the built manual, the model sweep's records, the harness build of the frontend (one folder per checkout: the layout scan opens it, the verification app embeds it, the browser server serves it) | 7 days |
| `e2e-lock/` | the e2e lock, present only while a heavy Playwright run holds it | scratch (3 days) |
| anything else (test scripts, screenshots, logs, `live*`, other `verify-*`) | scratch | 3 days |

Stale means deleted, by default: `tools/prune-stale.mjs` does it (`--dry-run` only lists), and it runs at the start of `verify-real-app.mjs` and `check.bat` and silently from the Stop hook. The age counts from the entry's `.last-used` marker (the harness writes it when it uses the entry), else from the newest top-level modification time. It deletes only entries directly inside `novira-data/work/`, never follows a link, and keeps an entry whose `novira.lock` is held or that a running process names, and everything while a verification `novira.exe` runs. Write your own scratch (test scripts, screenshots) to `novira-data/work/<name>`; do not rely on it staying.

## Rules that keep it safe

- Never stop the user's own `novira.exe` or its ComfyUI. Stop only the verification exe and the Python processes whose command line contains the verification copy.
- The verification window is visible on the user's screen, and they may use it. Before restarting it, check that it is idle (empty queue, nothing downloading), and do not drive it while a job of theirs runs.
- Check that the user is not using the GPU: `node tools/gpu-check.mjs` samples the load with `nvidia-smi` (exit 1 when the mean load of the busiest GPU is 25% or more, `NOVIRA_GPU_BUSY_PERCENT` to change it) and says who holds the lock. `verify-real-app.mjs` and `models-live.mjs` run it before they start and stop when the GPU is busy; ask the user, and only after they agree, set `NOVIRA_GPU_CHECK=0` to skip it. It does not judge memory (an idle ComfyUI keeps a model loaded) and reads only NVIDIA GPUs.
- GPU work takes the directory lock `NOVIRA_GPU_LOCK`: `mkdir` to take it, `rmdir` to release, wait while it exists. The app takes the same lock for its own jobs, so do not hold it by hand while a job runs in the app (the job would wait forever). A script that talks to ComfyUI directly takes the lock itself, and only after `mkdir` succeeded. The app records its own lock in a sibling `<lock>.owner` file (process id and start time), releases it on exit, and takes over a lock whose recorded process is gone, so a crash does not block the next start. A lock without that record belongs to someone else and is never removed by the app.
- Everything the harness generates stays under `novira-data/work/` (git-ignored with `novira-data/`; the folder does not exist until a run creates it). See "Where the harness writes".
- The user's models (`novira-data/models`) are shared, never copied or linked: the harness writes that folder into `modelRoots` of the verification data's `settings.json` (created if missing, merged if present, never duplicated). Tests must never delete files in it or install into it; a download goes to the verification data's own `models/`. Packs (video, music, voice...) kept in it are read through the same setting, so the isolated app sees them too. Do not create junctions or symlinks to it from a folder the harness deletes.
