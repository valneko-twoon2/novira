# 形式検証

テストでは調べきれない「すべての入力」「起こりうるすべての順序」を、機械に総当たりさせる手法。いまあるのは TLA+ によるキューの仕様の検査だけで、コードの検証（Kani）はまだ入れていない。一覧に戻る: [README.md](README.md)。

| 手法 | ここで確かめること | 場所 | 実行 | CI |
|---|---|---|---|---|
| モデル検査 / Model checking（TLA+、TLC） | 生成キューとワーカーの状態遷移。呼び出しとワーカーの各段階がどんな順に重なっても、実行中のジョブは同時に 1 つ、終わったジョブは動かない、消えた id は戻らない | `backend/crates/novira-core/formal/Queue.tla`、`Queue.cfg`、`scripts/tools/tla.mjs` | `node scripts/tools/checks.mjs tla` | `manual` |

## 何をするか

テストは、書いた入力か、乱数で選んだ入力だけを調べる。形式検証は、範囲を決めたうえでその中を残らず調べる。反例が無ければ「その範囲に壊れる場合は無い」と言え、あれば壊れる最短の手順が出る。

| 手法 | 調べる対象 | 証明の作り方 | 向く場所 |
|---|---|---|---|
| TLA+（TLC） | コードではなく、状態と遷移を書いた仕様 | 起こりうる状態をすべてたどる | 順序が絡む設計（キュー、ペアリングの状態） |
| Kani | 本物の Rust の関数 | 入力を「何でもよい値」として、性質を破る値を機械が探す | 入力が小さな型で、判定が単純な関数 |
| Verus | 本物の Rust の関数 | 人間が証明の筋道を書き、機械が検査する | 入れない（書く量が、この規模に見合わない） |

三つとも、人間が書くのは「守る性質」で、総当たりは機械がする（Verus だけ、証明の筋道も人間が書く）。

## 性質ベーステストとの使い分け

性質ベーステスト（proptest、fast-check）が既定で、入力が大きい、実行が重い、外とやり取りするものは、そちらに任せる。形式検証は置き換えではなく上乗せで、小さくて壊れると致命的な核にだけ足す。

- 入力が文字列、JSON、画像のように大きいもの、SQLite やファイルや ComfyUI を動かすものは、総当たりが終わらないか、上限が小さすぎて意味が薄い。性質ベーステストで調べる。
- 壊れる入力が広い範囲にあるなら、性質ベーステストですぐ見つかる。形式検証を足す意味は薄い。
- 形式検証が効くのは、特定の 1 点だけで壊れる小さな入力（整数、列挙型、短いバイト列）と、手順が長くないと現れない順序のバグ。

終わるかどうかは、事前には分からない。回してみて、数秒から数分で終わらなければ、上限を下げるか性質ベーステストに戻す。

## キューの仕様（`Queue.tla`）

`service/queue.rs` と `service/worker.rs` の動きを写した仕様。キューの各呼び出し（追加、取り消し、待機中の取り消し、全消去、整理、再試行、一時停止）は `queue_transition` のロックの下で 1 歩として扱う。ワーカーはロックを離す箇所ごとに別の歩にする（取る、開始する、実行する、終える）。この隙間で何が起きるかを調べるのが目的。

守らせている性質:

| 性質 | 内容 |
|---|---|
| `AtMostOneInProgress` | 実行中のジョブは同時に 1 つ |
| `InProgressIsTheWorkers` | 実行中のジョブは、ワーカーが持っているものだけ |
| `RunningMatchesWorker` | 状態の `running` は、ワーカーが持っているジョブを指し、持っていなければ空 |
| `NoItemBeyondNext` | まだ配っていない id のジョブは存在しない |
| `EndedStaysEnded` | 完了、失敗、取り消しのジョブは、もう状態が変わらない（消えるだけ） |
| `GoneStaysGone` | 消えた id は戻らない。再試行は新しい id で作る |

3 つの壊し方で、検査が実際に落ちることを確かめた。開始時の「待機中か」の確認を外す、完了で終わったジョブを上書きする、全消去で id の数え直しを許す。いずれも違反の手順が出る。コードを変えたら、仕様も同じ変更で直す。

実行は 1 秒ほど（ジョブ 4 つで、約 1.8 万の状態）。初回だけ、持ち運べる JDK 17 と `tla2tools.jar` を `novira-data/work/tools/` に取得する（TLC は Java 11 以上を要るため。システムの Java は変えない）。

## 限界

- 検査するのは仕様で、コードではない。仕様とコードのずれは、この検査では分からない。キューの実コードは `prop_queue.rs` などのテストが調べる。
- ジョブの順序は写していない。ワーカーは待機中の「どれでも」を取れるとして調べているので、実際の「先頭から」を含む。順序そのものの正しさは対象外。
- ジョブの中身、保存、通知は写していない。
- ジョブ 4 つまでの範囲。5 つ以上で初めて現れる誤りは、この検査では見えない。

## まだ入れていないもの

- Kani（コードの検証）。Windows のネイティブでは動かない。WSL の Ubuntu で動かすには、C コンパイラと Rust が要る。対象の候補は `backend/crates/novira-server/src/pair.rs` のペアリング（ペアリングコードの 1 回限りの使用、期限、セッションの時間切れ、レート制限、名前の検証）。`ring` に依存しているので、判定部分だけを切り出す必要が出るかもしれない。
- ペアリングの状態遷移の TLA+ 仕様。
