# CI: push ごとの検査

一覧に戻る: [README.md](README.md)

GitHub がブランチへの push ごとにリポジトリの検査を走らせるので、変更は開発者のマシンの外でも検査される。まっさらなランナーで確実に通る検査から始め、1 つずつ増やしている。

## 動作

- **名前。** 画面に出るワークフロー名は `Test`、`Audit`、`Supply chain`、`Release`。
- **トリガー。** どのブランチへの push、毎晩（03:23 JST。GitHub は既定ブランチでしか始めない）、手動。タグの push は代わりにリリースを走らせる（[01-release-workflow.md](01-release-workflow.md)）。同じブランチ・同じ種類のトリガーの新しい実行は、古い実行中の検査をキャンセルする。
- **`changes` ジョブ**（`ubuntu-24.04`）: `scripts/tools/ci-scope.mjs` が、push で変わったファイルから、長いジョブ（`vitest`、`clippy` と `cargo-test`、`e2e-chromium` と `e2e-phone`、`diff-backends`）が要るかを決める。要らないジョブは飛ばす。既定ブランチ、毎晩、手動、新しいブランチ（`before` が 0）、差分を読めないときは、すべて走らせる。`static` と `rust-format` はいつも走る。対応表は `ci-scope.mjs` の `RULES`。
- **`flaky` ジョブ**（`windows-latest`、最大 120 分、毎晩だけ）: Chromium の画面フローをリトライなしで 3 回ずつ走らせ、2 回目で通るだけのフローを見つける。
- **`static` ジョブ**（`ubuntu-24.04`、最大 20 分）: `frontend/` で `npm ci`、続いて `npm run typecheck`、`npm run lint`、`scripts/tools/check-eol.mjs`、`scripts/tools/check-name.mjs`、`scripts/tools/docs-check.mjs`、`scripts/tools/ui-refs.mjs`、`frontend/scripts/check-glossary.mjs`、`scripts/tools/changelog.mjs --check`。どれも前のものが失敗しても走るので、1 回の実行ですべての失敗が見える。
- **`rust-format` ジョブ**（`ubuntu-24.04`）: `backend/` で `cargo fmt --all -- --check`。ツールチェーンは `backend/rust-toolchain.toml`。
- **`vitest` ジョブ**（`windows-latest`、Node 22、最大 30 分）: `npm ci` のあと、`frontend/` で `npx vitest run --maxWorkers=4 --testTimeout=30000`（Playwright の spec ではなく、すべてのユニットテストとコンポーネントテスト）。ランナーは 4 コアで、設定の 10 ワーカーでは互いに飢えてテスト 4 件が 5 秒を超えた。このフラグはランナーだけに効き、自分で上限を設定しているテストはそれを保つ。
- **`clippy` ジョブ**（`windows-latest`、最大 60 分）: `backend/` で `cargo clippy -p novira-core -p novira-server -p novira --tests -- -D warnings`。cargo のレジストリと `backend/target` は `Cargo.lock` とツールチェーンのファイルをキーにキャッシュする。アプリのクレートのビルドスクリプトがフロントエンドをビルドするので、先に Node と `npm ci` を入れる。
- **`cargo-test` ジョブ**（`windows-latest`、最大 90 分）: `novira-core`、`novira-server`、`novira`（Tauri のシェル。コマンド一覧と capability の一致も検査する）に `cargo test --no-fail-fast`。各ステップは前のものが失敗しても走る。先にフロントエンドをインストールし（アプリのクレートがビルドする）、cargo は `clippy` と同様に、別のキーでキャッシュする。
- **`e2e-chromium` ジョブ**（`windows-latest`、最大 60 分）: `frontend/` で `npx playwright test --project=chromium`。モックのバックエンド上での Chromium による画面フロー（a11y 検査を含む）で、ワーカー 2（コアの半分、`playwright.config.ts`）、リトライ 1 回（`CI` が設定されている）。失敗した実行は `logs/playwright-report/` と `logs/e2e/` を成果物として 7 日間残す。
- **`e2e-phone` ジョブ**（`windows-latest`、最大 60 分）: `npx playwright test --project=phone --project=webkit`。スマホのレイアウト（`phone*.spec.ts`）を、Chromium の Pixel 7 と WebKit の iPhone 14 で。失敗時は同じレポートを成果物にする。
- **`diff-backends` ジョブ**（`windows-latest`、最大 60 分）: `node scripts/tools/diff-backends.mjs`。`novira-server`（エンジンなし）を `novira-data/work/server-target` に、フロントエンドのハーネスビルドと一緒にビルドし、空のデータフォルダでサーバーを起動して、それとブラウザのモックに対し `frontend/difftest/` を走らせる。cargo のビルドは別のキーでキャッシュし、いつも走る。キャッシュが省くのは依存だけなので、比較されるサーバーはこのコミットのもの。
- **テスト件数。** `vitest` と `diff-backends` のジョブは vitest の JSON レポートを書き（`--reporter=default --reporter=json`。`diff-backends.mjs` は `NOVIRA_VITEST_JSON` からファイルを取る）、`ci-summary.mjs vitest` を実行して、フォルダごととテストファイルごとの件数を書く。レポーターを指定すると、vitest 自身の形の違う要約も出なくなる。`cargo-test` ジョブは各クレートの出力をログに残し（`tee`）、最後のステップで `scripts/tools/ci-summary.mjs cargo` を実行して、すべてのテストバイナリの成功・失敗・無視の数をジョブの要約に書く。クレートごとの合計で、バイナリは折りたたみに入れる。2 つの Playwright ジョブは JSON レポーターを足し（`--reporter=list,html,json`）、`ci-summary.mjs playwright` を実行して、プロジェクトごとと spec ファイルごとの件数を書く。要約のステップはテストのステップが失敗しても走り、ログやレポートが無いときはそう書いた行を出すだけで、ステップは失敗にしない。`#[ignore]` のテスト（`*_live.rs`）は無視として数える。
- `static` と `rust-format` のジョブはソースを読むだけ。ビルドも、ブラウザも、GPU もない。

## 監査

`.github/workflows/audit.yml` は独立したワークフローなので、新しい勧告がすべての push を失敗させることはない。毎週月曜（03:17 UTC）と、`backend/Cargo.lock`、`frontend/package-lock.json`、`backend/.cargo/audit.toml`、このワークフローを変えるブランチの push で、`ubuntu-24.04` 上で走る。

- `cargo audit`（cargo-audit 0.22.2、`--locked` でインストールしてキャッシュ）を `backend/Cargo.lock` に対して。すでに判断済みの勧告は、それぞれ理由つきで `backend/.cargo/audit.toml` にある（[03-security.md](../01-core/03-security.md) の依存の指摘）。新しい脆弱性は実行を失敗させる。メンテナンス終了や unsound の警告は失敗させない。
- `frontend/` の `npm run audit`（`npm audit --omit=dev`）。アプリに同梱される依存。

## サプライチェーン

`.github/workflows/supply-chain.yml` は 3 つめのワークフロー。どのブランチへの push でも、手動（workflow_dispatch）でも、毎週月曜（03:43 UTC。GitHub はスケジュールを既定ブランチでしか始めない）にも走る。どちらのジョブも `ubuntu-24.04` で、バージョン固定のツールのリリースバイナリを GitHub のリリースからダウンロードし、実行前にワークフローに書いた sha256 と照合する（サードパーティのアクションも `cargo install` も使わない）。

- `cargo-deny`（0.20.2、最大 20 分）: `backend/` で `backend/deny.toml` を使い `cargo-deny --locked check --hide-inclusion-graph bans licenses sources`。グラフは Windows のもの（アプリは Windows のみで出す）。ライセンスはグラフが持つものの許可リストで、それ以外は失敗する。ワイルドカードのバージョン、未知のレジストリ、git ソースはすべて失敗し、1 つのクレートの 2 バージョンは警告だけ。ワークスペースのクレートは `publish = false` で、cargo-deny がそのパス依存をローカルとして扱える。勧告はここでは検査しない。`cargo audit` と `backend/.cargo/audit.toml` に任せる。
- `gitleaks`（8.30.1、最大 10 分）: `.gitleaks.toml` を使い、履歴全体（`fetch-depth: 0`）とツリーに `gitleaks detect --source . --redact`。既定のルールに、許可リストの 4 項目（それぞれ 1 つのファイルと 1 つの値に結びつき、理由を書いてある。テストのフィクスチャとカタログの id で、1 件ずつ確認済み）と、追跡されない `novira-data/` フォルダを足したもの。`--redact` は見つかった値を実行ログに出さない。コミット済みのシークレットの独自スキャン（`cargo test -p novira --test security`、`secrets`）は残る。ここで足すのは履歴と、既定のルールが持つ多数のキー形式。

手作業では: `cargo deny --manifest-path backend/Cargo.toml check bans licenses sources` と `gitleaks detect --source . --no-banner`（作業ツリーには `--no-git` も）。

## CodeQL

`.github/workflows/codeql.yml` が、コードの脆弱性を静的に調べる（GitHub の Code scanning。公開リポジトリは無料。結果は Security タブ）。

- **いつ回るか。** main と `release/**` への push、main 向けの PR、毎週火曜（04:29 UTC。GitHub は既定ブランチでしか始めない）。作業は `release/*` で行い、マージしたら消すので、`release/**` の push で回す。PR は main への取り込み前に止めるため。
- **言語。** `actions`、`javascript-typescript`、`python`、`rust`（GitHub のデフォルト設定と同じ）。ビルドはしない（`build-mode: none`）。言語ごとの `analyze` ジョブが並ぶ。
- **テストは見ない。** `.github/codeql/codeql-config.yml` の `paths-ignore` が、テストの置き場所（`tests/`、`tests.rs`、`*_tests.rs`、`#[cfg(test)]` のファズ `embedded/fuzz.rs`、`*.test.ts(x)`、`*.testkit.ts(x)`、`frontend/e2e/`、`frontend/difftest/`）を外す。テストの固定シードや、テストが出す秘密の値は、アプリの弱点ではない。ビルドなしの解析なので、Rust にも効く。テストの置き場所を増やしたら、ここにも足す。
- **デフォルト設定は使わない。** デフォルト設定は既定ブランチと、既定ブランチ向けの PR しか見ない。ワークフローと同時には使えないので、リポジトリの設定でデフォルト設定を無効にしてから、このワークフローを動かす。

## Dependabot

依存の更新は、脆弱性の通知と更新の PR を Dependabot に任せ、その PR の判断を `.github/workflows/dependabot-triage.yml` に任せる。

- **脆弱性の通知と security updates。** リポジトリの設定で有効にする（ファイルは持たない）。既知の脆弱性がある依存を直す PR が自動で出る。見つけるのは `Audit`、直す PR を作るのが Dependabot。
- **version updates。** `.github/dependabot.yml`。cargo（`/backend`）、npm（`/frontend`）、GitHub Actions（`/`）を毎週月曜 04:00 JST に確かめ、minor と patch は 1 つの PR（`minor-and-patch` グループ）にまとめる。major は 1 件ずつ別の PR。コミットの接頭辞は `chore`。PR の向き先は既定ブランチ（main）。`release/*` は版ごとに作って消すので、向き先に固定できない。main に入った更新は、次のマージでリリースブランチへ届く。
- **判断（`Dependabot triage`、`scripts/tools/dependabot-triage.mjs`）。** 4 時間ごと（と手動。手動は既定で `--dry`）に、開いている Dependabot の PR を 1 件ずつ見る。判断はタイトル、ラベル、経過日数、検査の状態だけで決まる関数で、`gh` を呼ぶのは `run` だけ。
  - 検査の状態は、head のコミットに対する `Test` と `Supply chain`（と、走っていれば `Audit`）の実行から決める。必須の 2 つが成功なら成功、どれかが失敗なら失敗、実行中なら保留、実行がなければ `none`。`cancelled`（新しい push に置き換えられた実行）は数えない。
  - minor と patch（と `minor-and-patch` グループ）で検査がすべて成功なら、squash でマージしてブランチを消す。
  - major は、検査に関わらず理由を書いて閉じる。人が変更を読むもので、Dependabot は次の major を別に出す。0.x の minor は major として扱う。
  - 検査が通らないまま 21 日開いている小さな更新は、閉じる（次の版で新しい PR が出る）。
  - `security` ラベルの PR は、規則では閉じない。小さくて検査が成功したものだけマージし、残りは人を待つ。
  - タイトルから版が読めない PR は、何もしない。

## 境界

| 境界 | ガード |
|---|---|
| トークン | `Test`、`Audit`、`Supply chain` は `contents: read` のみ。`Dependabot triage` だけが `contents: write` と `pull-requests: write` を持つ（PR のマージと閉じるため）。シークレットは使わない。スケジュール実行は既定ブランチのコードをリポジトリ自身のトークンで動かし、PR の中身を取り出して動かすことはない |
| ダウンロードするツール | サプライチェーンのツールはバージョン固定のリリースで、ワークフローで sha256 を検査する。バージョンを上げるときは、リリースから取った新しいハッシュを使う |
| アクション | GitHub 自身のもの（`actions/*`。CodeQL だけ `github/codeql-action/*`）だけをメジャーバージョンで指定し、Node 24 で動くリリースを使う（古いものは非推奨の警告を出す）。`release.yml` はまだ古いメジャーのまま。タグでしか走らないので、確認できる実行を待ってから上げる |

## 既知の限界

- 自動マージの安全は、`Test`・`Supply chain`・`Audit` に頼る。悪意のある更新はテストでは見つからないので、検査を通った minor と patch がそのまま main に入る。許容しているのは、大きな更新（major）は必ず人が読むこと、依存は lock ファイルで固定されること、`cargo deny` が新しいライセンス・レジストリ・git 依存を止めること。
- リポジトリ自身のトークンで起こした push は、別のワークフローを起動しない。自動マージで main が動いても `Test` は走らない（PR のブランチで通っている）。
- 検査が失敗しても、マージも push も止まらない。ブランチ保護はまだない。
- `vitest` ジョブが Windows で走るのは、ハーネスのテスト（`data-guard`、ハーネスのパス、モデルの総当たり、prune ポリシー）が Windows のパスを前提にしているため。Ubuntu ではそのうち 4 ファイルが失敗した。

## 未実装

- 次の候補。ランナーで通るのを確認してから 1 つずつ足す: レイアウトスキャンとビジュアルリグレッション（ベースラインは Windows の画像）。それまでは `scripts\check.bat` と `scripts\checks\full-check.bat` に残る。
- 週次の監査やサプライチェーンの実行が失敗しても通知は出ない。Actions タブに表示される。
- 夜の `flaky` ジョブはまだランナーで通るのを確認していない。落ちたら所要時間とリトライなしの失敗を見て調整する。
