# CI: PR ごとの検査

一覧に戻る: [README.md](README.md)

PR ごとにリポジトリの検査を走らせ、変更を開発者のマシンの外でも検査する。ブランチへの push ごとには回さない（[meta/astryx](https://github.com/meta/astryx) の CI と同じ考え方）。まっさらなランナーで通る検査から、1 つずつ増やしている。

## 動作

- **名前。** 画面に出るワークフロー名は `Test`、`Audit`、`Supply chain`、`Release`。
- **トリガー。** main と develop 向けの PR（開いた、更新した、開き直した、下書きから準備完了にした）、main と develop への push（マージ）、毎晩（03:23 JST。GitHub は既定ブランチでしか始めない）、手動。下書きの PR では何も走らない。それ以外のブランチへの push では走らない。タグの push は代わりにリリースを走らせる（[01-release-workflow.md](01-release-workflow.md)）。同じブランチ・同じ種類のトリガーの新しい実行は、古い実行中の検査をキャンセルする。Dependabot のブランチも PR として検査される。
- **`changes` ジョブ**（`ubuntu-24.04`）: `scripts/tools/ci-scope.mjs` が、push や PR（base との差分）で変わったファイルから、長いジョブ（`vitest`、`clippy` と `cargo-test`、`e2e-chromium` と `e2e-phone` と `e2e-visual`、`diff-backends`）が要るかを決める。要らないジョブは飛ばす。既定ブランチ、毎晩、手動、新しいブランチ（`before` が 0）、差分を読めないときは、すべて走らせる。`static` と `rust-format` はいつも走る。対応表は `ci-scope.mjs` の `RULES`。
- **`flaky` ジョブ**（`windows-latest`、最大 120 分、毎晩だけ）: Chromium の画面フローをリトライなしで 3 回ずつ走らせ、2 回目で通るだけのフローを見つける。
- **`static` ジョブ**（`ubuntu-24.04`、最大 20 分）: `frontend/` で `npm ci`、続いて `npm run typecheck`、`npm run lint`、`scripts/tools/check-eol.mjs`、`scripts/tools/check-name.mjs`、`scripts/tools/docs-check.mjs`、`scripts/tools/ui-refs.mjs`、`frontend/scripts/check-glossary.mjs`、`scripts/tools/changelog.mjs --check`。どれも前のものが失敗しても走るので、1 回の実行ですべての失敗が見える。
- **`rust-format` ジョブ**（`ubuntu-24.04`）: `backend/` で `cargo fmt --all -- --check`。ツールチェーンは `backend/rust-toolchain.toml`。
- **`vitest` ジョブ**（`windows-latest`、Node 22、最大 30 分）: `npm ci` のあと、`frontend/` で `npx vitest run --maxWorkers=4 --testTimeout=30000`（Playwright の spec ではなく、すべてのユニットテストとコンポーネントテスト）。ランナーは 4 コアで、設定の 10 ワーカーでは互いに飢えてテスト 4 件が 5 秒を超えた。このフラグはランナーだけに効き、自分で上限を設定しているテストはそれを保つ。
- **`clippy` ジョブ**（`windows-latest`、最大 60 分）: `backend/` で `cargo clippy -p novira-core -p novira-server -p novira --tests -- -D warnings`。cargo のレジストリと `backend/target` は `Cargo.lock` とツールチェーンのファイルをキーにキャッシュする。アプリのクレートのビルドスクリプトがフロントエンドをビルドするので、先に Node と `npm ci` を入れる。
- **`cargo-test` ジョブ**（`windows-latest`、最大 90 分）: `novira-core`、`novira-server`、`novira`（Tauri のシェル。コマンド一覧と capability の一致も検査する）に `cargo test --no-fail-fast`。各ステップは前のものが失敗しても走る。先にフロントエンドをインストールし（アプリのクレートがビルドする）、cargo は `clippy` と同様に、別のキーでキャッシュする。
- **`e2e-chromium` ジョブ**（`windows-latest`、最大 60 分）: `frontend/` で `npx playwright test --project=chromium`。モックのバックエンド上での Chromium による画面フロー（a11y 検査を含む）で、ワーカー 2（コアの半分、`playwright.config.ts`）、リトライ 1 回（`CI` が設定されている）。失敗した実行は `logs/playwright-report/` と `logs/e2e/` を成果物として 7 日間残す。
- **`e2e-phone` ジョブ**（`windows-latest`、最大 60 分）: `npx playwright test --project=phone --project=webkit`。スマホのレイアウト（`phone*.spec.ts`）を、Chromium の Pixel 7 と WebKit の iPhone 14 で。失敗時はレポートを成果物にする。
- **`e2e-visual` ジョブ**（`windows-latest`、最大 60 分）: `npx playwright test --project=visual`。全画面と各部品を、ダークとライトで、基準画像（`-win32.png`）と比べる。コミット時には回さない。見た目を変えたら、更新した基準を同じコミットに入れる。差分が多いときは、許容を緩めずユーザーに聞く。
- **`diff-backends` ジョブ**（`windows-latest`、最大 60 分）: `node scripts/tools/diff-backends.mjs`。`novira-server`（エンジンなし）を `novira-data/work/server-target` に、フロントエンドのハーネスビルドと一緒にビルドし、空のデータフォルダでサーバーを起動して、それとブラウザのモックに対し `frontend/difftest/` を走らせる。cargo のビルドは別のキーでキャッシュし、いつも走る。キャッシュが省くのは依存だけなので、比較されるサーバーはこのコミットのもの。
- **テスト件数。** `vitest` と `diff-backends` のジョブは vitest の JSON レポートを書き（`--reporter=default --reporter=json`。`diff-backends.mjs` は `NOVIRA_VITEST_JSON` からファイルを取る）、`ci-summary.mjs vitest` を実行して、フォルダごととテストファイルごとの件数を書く。`cargo-test` ジョブは各クレートの出力をログに残し（`tee`）、最後のステップで `scripts/tools/ci-summary.mjs cargo` を実行して、すべてのテストバイナリの成功・失敗・無視の数をジョブの要約に書く。2 つの Playwright ジョブは JSON レポーターを足し（`--reporter=list,html,json`）、`ci-summary.mjs playwright` を実行して、プロジェクトごとと spec ファイルごとの件数を書く。要約のステップはテストのステップが失敗しても走り、ログやレポートが無いときはそう書いた行を出すだけで、ステップは失敗にしない。`#[ignore]` のテスト（`*_live.rs`）は無視として数える。
- `static` と `rust-format` のジョブはソースを読むだけ。ビルドも、ブラウザも、GPU もない。

## 監査

`.github/workflows/audit.yml` は独立したワークフローなので、新しい勧告がすべての push を失敗させることはない。毎週月曜（03:17 UTC）と、`backend/Cargo.lock`、`frontend/package-lock.json`、`backend/.cargo/audit.toml`、このワークフローを変える main と develop への push と、両方に向けた PR で、`ubuntu-24.04` 上で走る。

- `cargo audit`（cargo-audit 0.22.2、`--locked` でインストールしてキャッシュ）を `backend/Cargo.lock` に対して。すでに判断済みの勧告は、それぞれ理由つきで `backend/.cargo/audit.toml` にある（[03-security.md](../01-core/03-security.md) の依存の指摘）。新しい脆弱性は実行を失敗させる。メンテナンス終了や unsound の警告は失敗させない。
- `frontend/` の `npm run audit`（`npm audit --omit=dev`）。アプリに同梱される依存。

## サプライチェーン

`.github/workflows/supply-chain.yml` は 3 つめのワークフロー。main と develop 向けの PR、両方への push、手動（workflow_dispatch）、毎週月曜（03:43 UTC。GitHub はスケジュールを既定ブランチでしか始めない）にも走る。どちらのジョブも `ubuntu-24.04` で、バージョン固定のツールのリリースバイナリを GitHub のリリースからダウンロードし、実行前にワークフローに書いた sha256 と照合する（サードパーティのアクションも `cargo install` も使わない）。

- `cargo-deny`（0.20.2、最大 20 分）: `backend/` で `backend/deny.toml` を使い `cargo-deny --locked check --hide-inclusion-graph bans licenses sources`。グラフは Windows のもの（アプリは Windows のみで出す）。ライセンスはグラフが持つものの許可リストで、それ以外は失敗する。ワイルドカードのバージョン、未知のレジストリ、git ソースはすべて失敗し、1 つのクレートの 2 バージョンは警告だけ。ワークスペースのクレートは `publish = false` で、cargo-deny がそのパス依存をローカルとして扱える。勧告はここでは検査しない。`cargo audit` と `backend/.cargo/audit.toml` に任せる。
- `gitleaks`（8.30.1、最大 10 分）: `.gitleaks.toml` を使い、履歴全体（`fetch-depth: 0`）とツリーに `gitleaks detect --source . --redact`。既定のルールに、許可リストの 4 項目（それぞれ 1 つのファイルと 1 つの値に結びつき、理由を書いてある。テストのフィクスチャとカタログの id で、1 件ずつ確認済み）と、追跡されない `novira-data/` フォルダを足したもの。`--redact` は見つかった値を実行ログに出さない。コミット済みのシークレットの独自スキャン（`cargo test -p novira --test security`、`secrets`）は残る。ここで足すのは履歴と、既定のルールが持つ多数のキー形式。

手作業では: `cargo deny --manifest-path backend/Cargo.toml check bans licenses sources` と `gitleaks detect --source . --no-banner`（作業ツリーには `--no-git` も）。

## CodeQL

`.github/workflows/codeql.yml` が、コードの脆弱性を静的に調べる（GitHub の Code scanning。公開リポジトリは無料。結果は Security タブ）。

- **いつ回るか。** main と develop 向けの PR（下書きのあいだは回らない）、main と develop への push（マージ）、毎週火曜（04:29 UTC。GitHub は既定ブランチでしか始めない）。
- **言語。** `actions`、`javascript-typescript`、`python`、`rust`（GitHub のデフォルト設定と同じ）。ビルドはしない（`build-mode: none`）。言語ごとの `analyze` ジョブが並ぶ。
- **テストは見ない。** `.github/codeql/codeql-config.yml` の `paths-ignore` が、テストの置き場所（`tests/`、`tests.rs`、`*.test.ts(x)`、`frontend/e2e/` など）を外す。テストの固定シードや秘密に見える値は、アプリの弱点ではない。Rust にも効く。置き場所を増やしたら、設定にも足す。
- **デフォルト設定は使わない。** デフォルト設定は既定ブランチ向けしか見ず、ワークフローと同時には使えないので、リポジトリの設定で無効にしてある。

## 境界

| 境界 | ガード |
|---|---|
| トークン | `Test`、`Audit`、`Supply chain` は `contents: read` のみ（`Dependabot triage` の権限は [03-dependabot.md](03-dependabot.md)）。シークレットは使わない。スケジュール実行は既定ブランチのコードをリポジトリ自身のトークンで動かし、PR の中身を取り出して動かすことはない |
| main | ブランチ保護。PR を通さない push を拒み、`Test` と `Supply chain` のジョブ（`changes`、`static`、`rust-format`、`vitest`、`clippy`、`cargo-test`、`e2e-chromium`、`e2e-phone`、`e2e-visual`、`diff-backends`、`cargo-deny`、`gitleaks`）が通らない PR のマージを拒む。飛ばしたジョブは通ったとみなす。CodeQL の解析（`analyze (*)`）は必須にせず、`pr.mjs` が終わるまで待つ。PR は下書きで開き、レビューが ok になってから `pr.mjs` が下書きを外す（下書きのときに飛ばしたジョブは数えない）。承認は求めない（エージェントはユーザーのアカウントで動き、自分の PR は承認できない。レビューは `scripts/tools/pr.mjs` のマージ条件が見る）。管理者（ユーザーとエージェント）にも効く。緊急時は、リポジトリの設定で外す |
| ダウンロードするツール | サプライチェーンのツールはバージョン固定のリリースで、ワークフローで sha256 を検査する。バージョンを上げるときは、リリースから取った新しいハッシュを使う |
| アクション | GitHub 自身のもの（`actions/*`。CodeQL だけ `github/codeql-action/*`）だけをメジャーバージョンで指定し、Node 24 で動くリリースを使う（古いものは非推奨の警告を出す）。`release.yml` はまだ古いメジャーのまま。タグでしか走らないので、確認できる実行を待ってから上げる |

## 既知の限界

- `vitest` ジョブが Windows で走るのは、ハーネスのテストが Windows のパスを前提にしているため（Ubuntu では 4 ファイルが失敗した）。
