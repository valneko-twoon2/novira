# 共有されてライブで追従する画面状態

一覧に戻る: [README.md](README.md)

ページがブラウザのストレージの `novira.*` に持つもの（生成フォーム、下書き、プリセット、プロンプトブック、設定）はバックエンドにも保存され、同時に開いているページは互いに追従する。保存した状態のリセットとバックアップ・復元は [01-settings-engine.md](../03-engine/01-settings-engine.md)。

## 動作

**画面状態はデスクトップアプリとブラウザ用サーバーで共有する。** ページがブラウザのストレージの `novira.*` に持つもの（設定、履歴、下書き、プリセット、プロンプトブック）は、データベースの `meta` テーブルにも 1 つの JSON オブジェクトとして保存される（`ui_state`、`backend/crates/novira-core/src/service/ui_state.rs`）。各シェルのストレージは別々で、両方が同じデータフォルダを開くため。起動時、ストアができる前に、`adoptBackendUiState`（`frontend/src/state/uiStateSync.ts`。`frontend/src/main.tsx` から呼ぶ）が `adopt_ui_state` を呼ぶ。バックエンドの状態が勝ち、ストレージに入る。まだ同期したことのないページは自分の状態を送る。バックエンドに状態が無ければそれがバックエンドの状態になり、あれば一度だけ `ui_state_replaced`（最新の 1 つだけ）に退避して置き換える。以後の `novira.*` キーの変更は、0.8 秒後とページが隠れたときに `save_ui_state` で送る。パッチとして、テキストが変わったキーだけと、無くなったキーを `removed` に入れて送り、バックエンドが保存済みの状態の上に重ねる（`patch_ui_state`）。タブを動かすクリックが送るのは数十バイトで、数百キロバイトの状態ではない（全状態を送るのは復元のときだけ）。読めないバックエンドの場合、ページはそのままで、そのセッション中は何も受け取らない。復元は、再読み込みの前に同じ方法で状態を保存する。ブラウザのモックはメモリにだけ持つ。

**ページ間のライブ同期**（`frontend/src/state/uiStateSync.ts`、`uiStateMerge.ts`、`rehydrate.ts`、`liveStores.ts`）。1 つのデータフォルダで同時に開いているページ（デスクトップアプリ、PC のブラウザのページ、ホームネットワーク経由のスマートフォン）は、動いている間、互いの保存した状態に追従する。

- *通知。* `save_ui_state` は保存するページ自身のランダムな ID（`origin`。英数字、`-`、`_` の 1〜64 文字で、それ以外は空に落とす）を受け取り、状態を保存したら `ui_state_changed { origin, revision }` を出す（`BackendEvent::UiStateChanged`。Tauri のイベントチャンネルと `/events` で）。`revision` は増えるだけ（ミリ秒で、同値なら 1 足す）。イベントは状態を持たない。ホームネットワークのデバイスもほかのイベントと同じように受け取る。
- *読み取り。* `origin` が自分のものでないページは、150 ms 後に `adopt_ui_state(null)`（新しいコマンドは無い）で状態を読む（連続した通知は 1 回にまとめる）。画面に戻ったとき（眠ったスマートフォンはイベントを逃す）と、イベントソケットが開き直ったとき（`queue_cleared`）にも読む。テキストはバックエンドと同じ検査にかける。`novira.*` のキー（200 文字以内）とテキストの値からなるオブジェクトで、32 Mi 文字以内。それ以外は無視する。イベントの 2 つの項目も検査し、既に見たものより新しくない revision のイベントは捨てる。
- *マージ（キー単位、最後の書き手が勝つ）。* ページはキーごとに、最後の読み取りか書き込みの時点のバックエンドのテキストと自分のストレージのテキストを覚える。キーがバックエンドに従うのは、バックエンドのテキストがそれ以後に変わり、ページのテキストが変わっていないとき。ページ自身が変えたキーはページのテキストを保ち、次に送るので、後の書き手が勝つ。選択はフィールド単位ではなくキー単位である。ストアがキー全体を保存するため（生成フォームは 1 つのキー）。直近 2 秒以内にページが書いたキーは保留にして 1 秒後に見直すので、入力中のテキストがカーソルの下で置き換わらない。バックエンドが落としたキーはストレージから消す。
- *適用。* 変わったキーをストレージに書き、その後ろのストアがそれを読み直す（`persist.rehydrate()`、`rehydrate.ts` 経由。ストアは `liveStores.ts` に一度だけ列挙する）。適用中の書き込みはページの変更ではなく、同期済みの記録は適用の後に取るので、ページは受け取ったものを送り返さず、2 つのページが同じ変更を行き来させることもない。ページ自身の保存は自分の `origin` 付きのイベントで戻ってくるが、読まない。
- *送信前。* パッチはこのページのキーだけを挙げるので、別のページが変えたキーの古いコピーを新しい上に重ねることはない。ページが送る前にバックエンドの状態を読むのは、最後に読んでからほかのページが保存したかもしれないとき（イベント、復帰、ソケットの開き直し）だけで、バックエンドを一人で使うページは何も読まない。送信に失敗したら次の変更で再試行する。
- *ページごとでライブでないもの。* 次のキーは保存された状態と一緒に運ばれる（次の起動はバックエンドのものを取る）が、動いているページは外からこれを変えない。`novira.settings`（言語、テーマ、ズームなどの設定）、`novira.gallery`（サムネイルサイズと表示の選択）、`novira.agent`（アシスタントのチャットとそのウィンドウ）、`novira.canvas`、`novira.workflows`、`novira.text`（編集中の文書）、`novira.extensions.railWidth`、`novira.mock.comics`、`novira.modelUpdates`。どのストアも登録していないキーは決して適用されず、保存された状態に読まれないまま残る（削除されたロゴ画面の `novira.logo` と `novira.logoPresets`。古いバージョンが保存した状態にある）。ほかの `novira.*` キーはすべて追従する。生成フォーム（プロンプト、モデル、LoRA、参照画像、サイズ、シードなど。`novira.params`）、下書き、画像、音楽、動画、音声、文字スタイル、文字テンプレート、キャラクターのプリセット、テキストタブから保存した画像のレイヤー（`novira.textSources`）、ランダムプリセット実行でチェックしたプリセット（`novira.presetRun`）、プロンプトブック、ワイルドカードの一覧、動画、音楽、音声、漫画仕上げのフォーム。ソースが書くキーを列挙し、どちらのグループにも無いキーがあれば失敗するテストがある。

**ギャラリーは要約から始まる。** `bootstrap` は `imagesSummary: true` を付け、すべての画像から `metadata` と `workflow` を除いて答える（`ImageDTO::summary`）。9000 枚の 12.6 MB のうち 9 MB がそれで、グリッドは使わない。`get_image_details`（1 回に最大 2000 名）が戻す。`galleryDetails.ts` は、選択中、表示中、比較中の画像、動画と音声の画像、検索を入力した後のすべて（プロンプトの中を探す。500 件ずつ）、アシスタントのギャラリーツールのために読む。詳細がまだ届いていない画像は、アップロードした画像のように、無いものとして表示する。追いつくページは持っている詳細を保つ。モックも同じように答える。

**バックエンドがライブで保つもの。** ボード、ギャラリーの画像、モデル、保存したワークフローは、ページのストレージではなくバックエンドにあるので、あるページの変更はイベントとして他のページに届く（`backend/crates/novira-core/src/types.rs`。`frontend/src/state/wiring.ts` で適用）。`boards_changed`（ボードの作成、改名、アーカイブ、削除の後の全一覧。選択中または自動追加のボードが消えたページは未分類に戻る）、`images_changed`（ボード、スター、ヘルパーフラグが変わった画像とゴミ箱から戻った画像、ギャラリーを出た名前。もともと無かった名前は送らない）、`models_changed`（モデルの編集か削除の後の全一覧。選択中のモデルが消えたら選択を外す）、`workflows_changed`（保存か削除の後のライブラリ全体）。新しい画像は既に `image_added`、新しいモデルは `model_added` である。変更したページも同じイベントを受け取るが、もう一度適用しても何も変わらない。拒否された変更は何も送らない。ネットワーク越しのページ（スマートフォン、ブラウザのページ）は、眠っている間やソケットが落ちている間イベントを逃すので、再び表示されたときやソケットが開き直ったときに `bootstrap` で読み直し、同じ方法で適用する（`frontend/src/state/backendCatchUp.ts`）。その読み取りの間に届いた画像は保たれる。

## 境界

| 境界 | 守り |
|---|---|
| 画面状態（`adopt_ui_state`、`save_ui_state`。`removed` 付きも） | `novira.*` キー（各 200 文字以内）とテキストの値からなる 1 つの JSON オブジェクトで、32 MiB 以内。`meta` テーブルに束縛パラメータで保存する前に検査する（パッチは、データベースのロックの下で、検査し、マージし、全体をもう一度検査する）。バックエンドはテキストの中身を読まない。保存が運ぶ `origin` は英数字、`-`、`_` の 1〜64 文字のときだけ保持するので、イベントがそれ以外のテキストを運ぶことはない。ページはイベントも取得した状態も信頼しないものとして扱い、両方をもう一度検査し、登録済みのストアが読むキーだけを適用する（`rehydrate.ts`）。 |

## 既知の限界

- 最初の同期で置き換えられた状態（`ui_state_replaced`）は、データベースからしか読めない。シェルごとに合う設定（ズーム、パネル幅）も起動時には共有されるが、ライブでは共有されない。
- ライブ同期はキー単位で最後の書き手が勝つ。2 つのページが同じキー（たとえばプロンプト）を約 1 秒以内に変えると、後の保存が残り、もう一方の変更は失われる。保存は、保存したページのページごとのキー（設定）も共有状態に入れるので、次にページが起動すると、最後に保存したページのものを取る。隠れたままやオフラインのページは、再び表示されたときに追いつく。モックとフェイクのバックエンドと本物のストアで検査した。本物のスマートフォンでは検査していない。
